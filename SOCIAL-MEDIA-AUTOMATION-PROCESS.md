# Social Media Automation — Process Document
**Skyline Travel Planner** · Instagram + Facebook · last updated **2026-08-05**

This is the operator's runbook for Skyline's social-media automation: what it does,
how a post travels from idea to published, the daily schedule, how you approve posts,
and how to operate / troubleshoot it. The code lives in
[`social-automation/`](social-automation/); this document sits at the project root as
the single at-a-glance reference.

> **One-line summary:** every day the system drafts grounded Skyline posts, sends you
> an **A/B card on WhatsApp**, and — once you reply **A / B / both** — publishes the
> chosen card to **Instagram + Facebook**. Nothing is invented, and nothing publishes
> without your approval.

---

## 1. The big picture

```
  INTAKE (3 channels)          GENERATE + REVIEW            APPROVE               PUBLISH
 ┌───────────────────┐      ┌────────────────────┐      ┌──────────────┐      ┌──────────────┐
 │ 1. WhatsApp photo │      │ caption grounded   │      │ A/B card sent │      │ Instagram    │
 │ 2. Vendor email   │ ───▶ │ in facts.js        │ ───▶ │ to WhatsApp   │ ───▶ │  +           │
 │ 3. Calendar ideas │      │ Fact-Check▸SMM▸QA  │      │ you reply A/B │      │ Facebook     │
 └───────────────────┘      └────────────────────┘      └──────────────┘      └──────────────┘
        cron-prep (7 PM IST) ─────────────────────────┘         │       cron-publish (9 PM IST)
                                                         you, on WhatsApp
```

- **Grounded, never invented.** Captions may only use facts from
  [`social-automation/facts.js`](social-automation/facts.js) (Skyline's real packages,
  routes, prices, WhatsApp). Flights/trains/buses/cabs are **referral-only** and can
  never be sold in a post — the validator blocks it.
- **Human-gated.** A post reaches Instagram/Facebook only after you approve it **and**
  the live gate is on (see §7).
- **A/B choice.** Card **A** = a real destination photo; card **B** = an AI-generated
  scene (or a branded decorative card if image generation is off).

## 2. The three intake channels

All three run inside the **7 PM IST prep cron** and drop a draft into the queue.

| # | Channel | How it's triggered | Produces |
|---|---------|--------------------|----------|
| 1 | **WhatsApp photo / note** | You send a photo or a short note to the Skyline WhatsApp number | A draft post built around your photo → approval card |
| 2 | **Vendor email** | A whitelisted supplier emails a promo (Gmail intake, `GMAIL_ALLOWED_SENDERS`) | A **reseller A/B card** — Skyline's own price + voice, never the vendor's markup |
| 3 | **Calendar auto-ideas** | Automatic — one Skyline package per day, rotating through packages that have a real photo | A **publishable A/B card** (real photo + AI scene) |

> Channel 3 is the engine of the system — it produces a ready-to-approve card every
> day with **zero input from you**. Channels 1 and 2 are for when you (or a supplier)
> have something specific to post.

## 3. The pipeline, stage by stage

Each queue row moves through these **statuses** (visible via `queue-peek.js`, §6):

| Status | Meaning |
|---|---|
| `planned` | An idea generated by the calendar, not yet drafted into a card |
| `drafting` | Caption being written/grounded |
| `pending_approval` | **Card sent to your WhatsApp — waiting on your reply** |
| `approved` | You picked A / B / both — queued for the next publish pass |
| `publishing` | Mid-publish |
| `published` | **Live on Instagram + Facebook** (stores the IG media id + FB post id) |
| `held` | Held by the QA agent or a render issue — needs a look, won't publish |
| `rejected` | You (or the system) rejected it — will never publish |
| `failed` | A publish attempt errored |

**The review team** (runs automatically during generation, before you ever see the card):
1. **Fact-Check** — every claim must trace to `facts.js`; invented prices/attractions are stripped.
2. **Social Media Manager (SMM)** — caption quality, hook, structure, brand voice.
3. **QA safety-net** — holds a post that doesn't fulfil the request or fit the brand.

## 4. The daily schedule (automatic)

Two Vercel cron jobs run every day (times in IST, the owner's timezone):

| Cron | Time (IST) | Time (UTC) | What it does |
|------|-----------|-----------|--------------|
| **cron-prep** | **7:00 PM** | 13:30 | Runs all 3 intakes → generates + reviews → **sends approval cards to your WhatsApp** |
| **cron-publish** | **9:00 PM** | 15:30 | Publishes everything you **approved** to Instagram + Facebook |

**The 2-hour gap is your approval window.** Approve a card between 7 PM and 9 PM and it
goes out the same night automatically. Approve it *after* 9 PM and it waits for the
next night's publish cron (or publish it manually — §6).

Schedule is defined in [`social-automation/vercel.json`](social-automation/vercel.json).

## 5. How you approve — WhatsApp reply commands

When a card arrives you'll get **three messages**: card **A** (real photo), card **B**
(AI scene), and a caption + a **4-digit code** (e.g. `6877`). Reply with:

| Reply | Effect |
|---|---|
| `A 6877` (or `photo 6877`) | Approve — post the **real-photo** card |
| `B 6877` (or `scene 6877` / `decor 6877`) | Approve — post the **AI-scene** card |
| `both 6877` | Post **both** cards |
| `approve 6877` (or `yes` / `ok`) | Approve — defaults to card **A** |
| `reject 6877` (or `no`) | Discard — never publishes |
| `hold 6877` | Set aside for later |
| `edit 6877 <new caption>` | Replace the caption, then approve |

**Shortcut:** if only one card is waiting, you can reply **without the code** — a bare
`A`, `B`, `both`, `approve`, or `reject` applies to that single card.

The code is stable (the same card always maps to the same 4 digits). Your reply hits
the WhatsApp webhook and is applied automatically.

## 6. Operating it manually (from `social-automation/`)

All commands need the secrets unlocked first. In **PowerShell**:

```powershell
cd "C:\Users\PiyushM\OneDrive\Documents\WebSite_looknbooks\Skyline Travel Planner Launch\social-automation"
$env:SECRETS_PASSPHRASE = 'your-passphrase'   # use single quotes so PowerShell doesn't eat a $
```

| Task | Command |
|---|---|
| **See the queue** (all statuses) | `node automation/queue-peek.js` |
| See one status | `node automation/queue-peek.js pending_approval` |
| Inspect one row | `node automation/queue-peek.js recXXXXXXXX` |
| **Run a prep pass now** (drafts + sends cards) | `node automation/run.js prep` |
| Run just the calendar cards | `node automation/run.js calendar-cards` |
| Run just the email intake | `node automation/run.js email` |
| **Publish approved posts — DRY RUN** (safe preview) | `node automation/run.js publish` |
| **Publish approved posts — LIVE** | `$env:SOCIAL_LIVE='true'; node automation/run.js publish` |

> A publish is a **dry run** unless `SOCIAL_LIVE=true`. The dry run prints exactly what
> *would* post — always eyeball it first.

## 7. The live gate — why a post might NOT publish

Publishing requires **all three** to be true (any one missing → dry run, nothing posts):

1. `SOCIAL_LIVE=true`  — the master switch (set by hand, never auto-pushed)
2. the client (`skyline`) is marked `live: true` in
   [`clients.js`](social-automation/automation/clients.js)
3. real Meta credentials are present (`META_PAGE_TOKEN`, IG user id, etc.)

This is the deliberate safety design: even a fully-working queue cannot post to a real
account by accident.

## 8. Configuration & secrets

Secrets live **encrypted** in `social-automation/.env.enc` (AES-256-GCM), unlocked by
`SECRETS_PASSPHRASE`. They are **never** committed in plaintext.

**Editing secrets** (never put a secret on the command line or in chat):
```powershell
node automation/secrets.js open       # decrypt to a temporary plaintext .env
notepad .env                          # edit values
node automation/secrets.js encrypt    # re-encrypt back to .env.enc
Remove-Item .env                      # delete the plaintext
node automation/secrets.js check      # confirm it decrypts (no values shown)
```

**Syncing secrets to production** (values go via stdin, never a command line):
```powershell
node automation/push-env-to-vercel.js skyline-social --scope full-firm --target production
```
> `SOCIAL_LIVE` is intentionally **not** pushed by that script — set it by hand in Vercel.

**The env vars that matter:**

| Group | Keys | Purpose |
|---|---|---|
| Queue | `AIRTABLE_API_KEY`, `AIRTABLE_BASE_ID` | The Airtable `Queue` table (the store) |
| WhatsApp | `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_TO` | Approvals + photo intake. `WHATSAPP_TO` = the number that **receives** approval cards |
| Meta | `META_PAGE_TOKEN`, `META_PAGE_ID`, `META_IG_USER_ID` | Publishing to FB Page + Instagram |
| Images | `OPENAI_API_KEY`, `BLOB_READ_WRITE_TOKEN` | AI scene generation (card B) + image hosting |
| Email | `GMAIL_*`, `GMAIL_ALLOWED_SENDERS` | Vendor-email intake (optional) |
| Gate | `SOCIAL_LIVE`, `SOCIAL_CLIENT`, `CRON_SECRET` | Live switch, client selector, cron auth |

## 10. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| **No approval cards arriving on WhatsApp** | Expired/invalid WhatsApp token (Meta error `190`, subcode `467` "user logged out") | Regenerate a **permanent System User token** (see §11), update `.env.enc` + Vercel, redeploy |
| Cards go to the wrong phone | `WHATSAPP_TO` is an old number | Update `WHATSAPP_TO` in `.env.enc` **and** Vercel prod, redeploy |
| Send fails with `131047` | Outside the 24-hour window | From the recipient phone, send any message ("hi") to the Skyline WhatsApp number to open the window |
| Send fails with `131030` | Recipient not allow-listed (Meta **test** numbers only reach ≤5 saved numbers) | Add the number in Meta → WhatsApp → API Setup, or register a real business number |
| `publish` only ever dry-runs | Live gate off | Check §7: `SOCIAL_LIVE=true`, client `live:true`, creds present |
| Queue shows `store: memory` / empty | `SECRETS_PASSPHRASE` not set or wrong | Set it in the **same** shell; in PowerShell avoid `$` in the value or use single quotes |
| A card is stuck in `held` | QA agent held it, or a render/photo issue | Inspect the row (`queue-peek.js recXXX`) — read `reviewNotes` / `lastError` |
| Instagram publish error `9007` | IG media container not finished | Handled automatically (`waitForContainer` polls until ready); retry if it persists |

**Quick health checks:**
- Is the token valid? Call Meta's `debug_token` with the token — a healthy one is
  `is_valid: true`, `type: SYSTEM_USER`, `expires_at: 0` (never).
- Did the crons run? Vercel dashboard → `skyline-social` → **Cron Jobs** (last run) +
  **Observability → Logs**.

## 11. Maintenance & good habits

- **WhatsApp token:** always use a **System User** token with expiration **Never**
  (Business Settings → System Users → Generate token → scopes
  `whatsapp_business_messaging` + `whatsapp_business_management`). Temporary tokens from
  the "API Setup" page die every 24h — do not use them.
- **Approve before 9 PM IST** so the publish cron picks it up the same night.
- **Rotate `SECRETS_PASSPHRASE`** if it's ever exposed (open → re-encrypt with a new
  one → update Vercel). Pick a passphrase with **no `$`** (PowerShell mangles it).
- **Add destination photos** to widen the calendar rotation: add the destination to
  `DESTINATIONS_WITH_IMAGES` in `facts.js` and drop the photo in the images asset set.
  Only packages with a real photo are used for the daily card.
- **Keep `facts.js` in sync** with the live Skyline site — it's a manual mirror; when a
  package or price changes on the site, update `facts.js` too.
- **Current WhatsApp sender is a Meta test number** (`+1 555-…`) — fine for an
  owner-only approval channel (≤5 allow-listed recipients). To send approvals to
  teammates too, register a real business phone number in Meta.
